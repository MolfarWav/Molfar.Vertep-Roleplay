# Couplings and traps (Roleplay app)

Purpose: this map names what is tied to what in the Roleplay app, which invariant must stay true, where it is enforced, and which test fails when it breaks. It is for a person or a session that changes one area and must not forget a link.
One entry per area. Each entry points to the area's docs (`AGENTS.md`, `docs/ARCHITECTURE.md`, `docs/ENTITY-REGISTRY.md`, `docs/DATA-FORMATS.md`) and writes down only what falls between them or is easy to forget.
A test that checks the pointers (paths and symbols named here must exist) is planned in MolfarWav/Molfar.Vertep#247; until it lands, check them by hand when you touch an entry.
Update the entry in the same change that touches the area.
Date: 2026-11-05.

### Shared code copied into plugins
- **Touches:** `src/lib/entity-registry.js` (source) and the copies in `plugins/relations`, `plugins/world`, `plugins/litopys`; `plugins/agents/plugin.js` (generated agent-check and agent-run block); `src/lib/forge-recipes.ts` (generated from `.skills/agent-craft/references/`).
- **Must stay true:** each generated block is byte-equal to its source (line endings aside). A plugin cannot import another plugin, so the copy is the only way to share code. Never edit a generated block by hand; edit the source and run the script.
- **Enforced in:** `scripts/sync-registry.ts` `PLUGINS` `BEGIN` `outOfDate` `withBlock`; `scripts/sync-agents-plugin.ts` `BEGIN`; `scripts/sync-agent-recipes.ts` `generated`.
- **Fails in:** `test/rp-entity-registry.test.ts` (case "each plugin carries exactly the source"); `test/rp-agents-plugin.test.ts`; `test/rp-forge.test.ts`.
- **Why / history:** `docs/ENTITY-REGISTRY.md` ("Finding the entity a word means") gives the reason: one function, copied because plugins cannot import each other.
- **Trap:** the sync check reads only the plugins listed in `PLUGINS`. A new plugin that needs `resolveName` must be added to that list, or no test sees its copy. A fix made by hand in one copy is overwritten at the next sync.

### Chat transcripts on disk (Molfar.Vertep#537)
- **Touches:** `src/lib/chat-store.js` (source) and its copies in `plugins/engine`, `plugins/agents`, `plugins/direction`, `plugins/letters`, `plugins/litopys`, `plugins/meanwhile`, `plugins/polish`, `plugins/relations`, `plugins/studio-import`, `plugins/world`; the meta's `transcript` record; `chats/<id>.parts/`; `GET /chats` (the list reads the record, not the transcripts); `scripts/director-bench.ts`, `scripts/sensor-replay.ts`, `scripts/chat-join.ts`.
- **Must stay true:** every read and write of a transcript goes through the store: `chatRead`/`chatMessages` (all parts and the tail, full shape) and `chatSave`, `chatRemove`. A meta written by other code keeps `transcript` as it was read (spread the meta, never rebuild it), or the store has to look for the parts on disk. A save writes a new part before the tail gives up its messages, so a reader in the middle sees a message twice, never a hole.
- **Enforced in:** `scripts/sync-chat-store.ts` `PLUGINS` `outOfDate`; `chatSave` `chatPlan` `chatCollect`.
- **Fails in:** `test/rp-chat-store.test.ts` (the copies match; no plugin reads or writes a `.jsonl` outside the store; a reader in the middle of a save); `test/rp-data-formats.test.ts` (case "chats").
- **Why / history:** Molfar.Vertep#537: every send rewrote the whole file, a long chat hit the engine's 4 MB write cap, and the chosen text was stored twice.
- **Read on touch:** a read gives the messages of closed parts as stand-ins (`chats/<id>.parts/index.json`) that read their part when a heavy field (`CHAT_HEAVY`: `text`, `swipes`, `extra`, ...) is first read or set; `chatSave` leaves a part none of whose stand-ins was touched. A reader that loops over every message's `text` (a filter before a `slice(-n)`, a sum of all lengths) reads every part again on each call: walk back from the newest message, or keep the result by `chatOrigin` (engine `revealScans` for reveal words, Litopys `checkedChapters` for chapter sigs). `test/rp-chat-store.test.ts` ("old parts are read on touch", "readers that keep what old parts gave") checks both.
- **Trap:** `<id>.jsonl` alone is only the newest part of a long chat. Code that lists `chats/` must skip `<id>.parts` folders (filtering by `.meta.json` or `.jsonl` does). A new plugin that reads chats must be added to `PLUGINS`.

### A chat on the page, by pages (Molfar.Vertep#537)
- **Touches:** `src/lib/chat-page.ts` (`chatTail`, `mergeTail`, `prependPage`, `messageTotal`, `hasOlder`); the store's `ensureChatMessages` (`{ whole }`), `loadEarlierMessages`, `refreshChat`, the hydrate and the commit watch (`src/lib/store.ts`); `Chat.firstIndex`, `total`, `olderUse` (`src/lib/types.ts`); the engine's `GET /chats/:id?tail=N`, `GET /chats/:id/messages`, `/bootstrap?chat&tail` (`chatPage`, `pageLimit`); the chat view (`chat-view.tsx`: "Load earlier", find, bookmarks, select all, the header's totals) and `message-row.tsx` (the shown number).
- **Must stay true:** `chat.messages` may be the newest messages only: `firstIndex` says where they start. A number shown to the user, a dice roll's place and the opening hint count from the chat's start (`firstIndex + i`); a place used only on the page (the swipe animation, the regex depth from the end) stays the index in `messages`. A count of the chat is `messageTotal`, never `messages.length`. A feature that reads every message (find, bookmarks, select all, export, a whole-chat translation, the scene picker, Manage chats, the Chats page panel) calls `ensureChatMessages(id, { whole: true })` first. A refresh merges (`mergeTail`) rather than replacing, so the reader keeps the older pages loaded.
- **Enforced in:** `mergeTail` `prependPage` `pageFields`; `chatPage` in the engine.
- **Fails in:** `test/rp-chat-page.test.ts` (the routes, the merges); `test/rp-chat-snapshot.test.ts`; `test/rp-stream-stop.test.ts` (their stubs answer `?tail=`).
- **Trap:** a new place that loops over `chat.messages` to count or search the whole chat sees only the pages held: count with `messageTotal`, or load the whole chat first. Effects keyed on `messages.length` also fire when an older page is put in front: key them on the newest message's id.

### Names in helper requests (`expandNames`, #156)
- **Touches:** `expandNames` in `plugins/litopys`, `plugins/relations`, `plugins/world`, `plugins/letters`, `plugins/agents` (five copies, same body); `helperNames` in litopys, relations, world and agents (each reads the chat's persona and, for a solo chat, the card), `expandNamesFor` in relations and world; the request builders that take `names` (litopys `buildWorkerRequest`, `buildArcRequest`, `buildConsolidateRequest`, `buildSummaryRequest`; letters `buildLetterRequest`); the sends in relations `askSensor`, `askLeakCheck`, `askSoul`; world `buildAsk` and the World DM `ask`; agents `stepRun` and the dry run.
- **Must stay true:** only the copy of the text sent to a helper model changes. `{{user}}` becomes the persona name and `{{char}}` the card name, and only when the chat has one character (not a group); an empty name leaves its macro raw. Other macros (`{{if}}`, `{{getvar}}`, preset variables) stay raw. Chat messages, cards, personas, lorebooks and what the helpers store are never rewritten. Profile (its helpers keep `{{char}}`/`{{user}}` in the saved card), Polish and the World opening (its draft is saved as the chat's first message) are not touched. The system prompt is not expanded, only the input.
- **Enforced in:** the five `expandNames` copies (each `export`ed); `helperNames` per plugin; the call sites above.
- **Fails in:** `test/rp-helper-names.test.ts` (the table: all five copies agree; the litopys worker request, the relations and world names, and the letter request carry the real names). There is no byte-equality script for this copy, so a wording change in one copy passes unless its behaviour changes; keep the copies line for line.
- **Why / history:** #156. The main chat expands macros (`expandMacros`), but the helper calls sent the raw text, so the helper model read `{{user}}` literally. Plugins cannot import each other, so each one carries its copy.
- **Trap:** a helper call without a chat (World requests with no chat meta, the Letters "unplayed" and "nosoul" letters) has no persona name: `{{user}}` stays raw there on purpose. Letters' `{{char}}` is the card's name, except for an idle letter from a group chat. Relations' `userNameOf` returns the sentinel "the user" when there is no name; it is turned into "" before expansion, so the sentinel never reaches a model as a name.

### World DM rollback follows the chat's line
- **Touches:** `plugins/world/plugin.js` (`reconcile`, `firstGone`, `eventLost`, `pushSnap`, `CORE_KEYS`, `POST /world/rollback`, the calls in `updateRoute` and `llmRequest`); `src/lib/world.ts` (`rollbackWorld`, `worldSettling`); `src/lib/store.ts` (delete, swipe, regenerate, and `runGeneration` waiting for it).
- **Must stay true:** every field a DM run changes in the state is in `CORE_KEYS` (or is meant to survive a rollback: settings, `log`, `usage`, `dropped`). A run is undone when the message it read up to (`id#swipe`) is no longer on the chat's line; an empty read of the chat undoes nothing. Ids (`nextId`, `nextFront`) never go back. A hand edit survives while it is the record's latest change.
- **Enforced in:** `plugins/world/plugin.js`; `test/rp-world-rollback.test.ts`.
- **Fails in:** `test/rp-world-rollback.test.ts`.
- **Why / history:** #75 (prior art: Game Manager ST and Arbiter keep a snapshot per message).
- **Trap:** a new state field added to `normalizeState` and a run, but not to `CORE_KEYS`, is left behind when a reply is swiped. The entity registry (`data/registry/<chatId>.json`) is not rolled back.
- **Cast deck (#424, step 4):** `cast` (the cards), `castBuild` and `castLog` are in `CORE_KEYS`. A card becomes a record when the judge says `came` or `mentioned`, in the `llmRequest` hook (it also joins the registry and rewrites the world book there), outside any DM run's snapshot: a rollback to an older snapshot takes the record away and puts the card back, as it was then. A new route that changes the deck (`/world/cast/refill`, `/world/cast/cards`) saves the state like the records route does. The note of a new person carries the card's text, so the insert ceiling row `world cast` is 160 tokens, or, with the switch on and cards left, the longest card's text and want over 3.5 plus 110 (`deckNoteTokens` in the world plugin and the same rule in the engine plugin's `hookInsertBreakdown`: change both; `test/rp-insert-ceiling.test.ts` keeps them equal).
- **Cast (#424):** `entrance` and `lastEntrance` are in `CORE_KEYS`; `reconcile` treats `entrance` like `event` (a carrier reply that is gone sends it again with `sent: 0`, the dice kept). The silence is never stored: it is read from the chat and the Dashboard's snapshots, so a swipe or a delete cannot corrupt it. The insert ceiling row `world cast` (160 tokens, when `settings.cast` is not off and the level is not off) is written twice, in `plugins/world/plugin.js` `insertCeiling` and in `plugins/engine/plugin.js` `hookInsertBreakdown`: change both.

### The DM's memory: levers, rules for all chats, the lazy apply (#425)
- **Touches:** `plugins/world/plugin.js` (`learnEvidence`, `raiseProposals`, `answerProposal`, `addRule`, `removeRule`, `editRule`, `resetLearned`, `syncGlobalRules`, `loadState`, `learnNote`, `thingAllowed`, `learnedRoute`, `cleanLearned`); `src/lib/world.ts` (`WorldLearned`, `loadLearned`, the answer calls); `src/components/world/world-memory.tsx`, `world-view.tsx`, `world-profiles.tsx`, `world-controls.tsx`.
- **Must stay true:** `state.learned` and `state.signals` are NOT in `CORE_KEYS` (a swipe never undoes what the player answered or removed). A rule is an exact setting (`things`, `textMax`, `cast`) and only tightens; the rules for all chats live in `world/learned.json` and reach a chat in `loadState` (in memory, kept by the next save), remembered in `learned.applied` with the value they replaced, so Remove gives it back only where the chat still holds the rule's value and a value the player set by hand afterwards wins. Rules do not travel with a saved world (`cleanWorld` keeps `settings`, so the value the rule set rides along; the rule does not). A new lever needs: a key in `LEARN_LEVERS`, `leverValid`, `leverStricter`, evidence in `learnEvidence` (a share of the DM's own records, not a count), a sentence in `src/lib/i18n.ts` (`world.mem.p.*`, `world.mem.q.*`, `world.mem.rule.*`, `world.mem.lever.*`) and a row in the Add-a-rule form.
- **Enforced in:** `plugins/world/plugin.js`; `test/rp-world-learn.test.ts`, `test/rp-world-memory-render.test.tsx`.
- **Fails in:** the same tests.
- **Why / history:** #425 (owner, 2026-11-16: the first proposals only in code, a share not a count, the answer flips an exact setting; prose rules by a model come in the second half).
- **Trap:** a person drawn from the deck needs `src: "deck"` (set in `drawCard`) or the cast lever never sees a delete; a new record field also goes into `peekRoute`. A `loadState` on a chat with no state file applies the rules to the defaults, and `startSettings` may then overwrite `cast` from the profile: the rule reaches it the next time the chat is read.

A muted card entry is skipped only in the chat whose world book names it (`ownerChatId === meta.id`); the card's book itself is never changed. Only a swipe of the reply that carried the event counts (a deleted or failed reply sends it again, as before); the second swipe drops it. ### World DM and Dashboard shared ids
- **Touches:** the World DM records (`n#` ids, `ref` on a record); the scene tracker's `state.regIds` in `plugins/relations` and `plugins/world`; `src/lib/entity-registry.js`.
- **Must stay true:** when the DM ties its record to a thing or place the tracker knows, the record carries the registry id in `ref`, whatever language the story uses. `regIds` maps each tracker id to a registry id. Holder and location fields are still names today (`docs/ENTITY-REGISTRY.md`, "Why"); a new field stores the id.
- **Enforced in:** `plugins/world/plugin.js` `regIds` (state key) and the `ref` handling (`linkToRef`, `placeTwin`, `spotPair`, `trackedThings`); `plugins/relations/plugin.js` `regIds`.
- **Fails in:** `test/rp-registry-bridges.test.ts`, `test/rp-world-place-ref.test.ts`.
- **Why / history:** #240 (registry phase B: things and places); #514 (a ref on a second record of the hall took the forest's id and the story's place stood on the hall).
- **Trap:** renaming a place or thing by a string match in one plugin splits the two lists again. Go through `regIds`. A place record that shares a name or alias with another place record (`placeTwin`) never takes a ref: names in two alphabets cannot be compared by words, so a ref is the one thing a weak DM model can get wrong and the registry id then collects the wrong record's names. One record holds an id, except a spot whose `inside` names the record that holds it (`spotPair`); `placeRecordOf` prefers the spot, so the "here" is the spot while the tracker's text is the whole place. `trackedThings` offers a linked place id again when its text has two levels and unlinked place records exist.

### Hook insert reserve (history budget)
- **Touches:** every sibling plugin that adds text after assembly: `plugins/relations` (Dashboard block, "said" block, journal), `plugins/litopys` (story insert, backstory, card, persona and world memory, habits, recollections, who-knows-what, hidden plan, word-for-word passages), `plugins/world` (here note, event, dice), `plugins/agents` (inserts file). The history budget in the engine's reply path.
- **Must stay true:** each block a sibling can add has one row in `hookInsertBreakdown` with the most it can take in this chat. A block the chat has switched off, or the chat cannot have, counts 0. The history budget takes away the sum (`hookInsertReserve`). The Litopys row follows the memory size mode: `auto` is the default, so the row is 15% of the window (800 to 16000) plus 100, and a saved `budget` with no `budgetMode` stays fixed; this rule is written twice (Litopys `budgetModeOf`, engine `hookInsertBreakdown`), change both. The two rows "who knows what" and "hidden plan" count when the reply voices several characters: a group, or a chat whose card has several names (the card's name, data.name and molfar_soul.characters keys). That second condition is written twice: Litopys `soleVoice` (null for several names) with `cardNamesOf` and `recollectors`, which decide whether `castKnowledgeFor` runs, and engine `hookInsertBreakdown` (`cardNames`, `severalVoices`). Change both.
- **Enforced in:** `plugins/engine/plugin.js` `hookInsertBreakdown` `hookInsertReserve`.
- **Fails in:** `test/rp-hook-reserve.test.ts`. It checks the numbers of the rows it knows, and the several-names rule for a chat with a card (a card with one name does not reserve the two rows). No test compares a real insert with its row, so a new sibling block with no row passes.
- **Why / history:** #184 (the breakdown comment cites MEMORY-INJECTION 13.1).
- **Trap:** a new insert in a sibling with no row here is not reserved, so the window overflows silently, and no test compares a real insert with its row (#248, item 5; the structural fix is the `insertCeiling` hook, #220). The row "dashboard said" follows the switch `plugin:said` since #248.

### Word-for-word recall of the chain's earlier chats (#184 step 8)
- **Touches:** `recallBuild`, `recallIndexChat`, `recallRefresh`, `recallCandidates`, `verbatimFor`, `verbatimRows`, the `llmRequest` block, `pruneOrphans` (dir `litopys/recall/`), `linkRoute` (the index is made at the link), `recallMissed` and its `.none.json` marker, `recordLitFired` / `firedRoute` (the whole-chat counter), `meaningRegions` (door B, reads the chapter vectors of `.cache/litopys/vectors/`), `recallPassages` (a chunk's text read from the chat through the chat store, `.q.json`), `recallSigOf`, the passage vectors of door B (`loadRecallVectors`, `wantRecallVectors`, `kickRecallWant`, `finishRecallBatch`, `.cache/litopys/recall-vectors/`, the `rv_` request in `kickEmbedWants` and its `lit_rv_` answer in `onTick`), config `verbatimMeaning` / `verbatimMeaningZ`, `onTick` (`recallRefresh`), config `verbatim` / `verbatimBudget` (`plugins/litopys`); the board key `plugin:verbatim`, its omit and board rows, and the reserve row "litopys verbatim" (`plugins/engine`); the Memory view fold (`src/components/memory/trace-parts.tsx`, `src/lib/memory-trace.ts`); the Fired panel's whole-chat fold (`src/components/chat/fired-tabs.tsx`, `src/lib/fired.ts`).
- **Must stay true:** door B (meaning) is off by default and can only choose which chapter to look in: a passage needs a rare word of its own, so vectors alone never add text (the DB-vec calibration: an unrelated question's best match is as close as a relevant one's). It is on by default (only an explicit `verbatim: false` turns it off, in `loadConfig`, the Settings switch and both `plugins/engine` reads) and costs nothing when off (no index, no read of another chat); a chat that continues nothing gets nothing. It reads the whole chain, nearest chat first, and only a chat that continues another gets a part. A passage is let in by rare shared words only, never by vectors, and only when the chance that it shares that many words by luck is small (`RECALL_CHANCE`); the rule is independent of the length of the chat and of the scan. A passage carries the `cast` of its chapter, so a character that did not witness the scene does not get it (the same `witnessed` as the story insert). It sits above the facts and says that the facts and later events win. It follows "start clean" and its own switch. Its two index files stay under 3.5 MB and hold no text: a chunk's text is read from the chat (`chatMessages` stand-ins), never across a closed part, and is shown only while its hash matches. Inside an open chapter a vector only orders the passages that share a word; vectors are asked for only for an opened chapter's passages, never for a whole chat.
- **Enforced in:** `plugins/litopys/plugin.js` (the functions above); `plugins/engine/plugin.js` `hookInsertBreakdown`, `PROMPT_BOARD_OFF_KEYS`.
- **Fails in:** `test/rp-verbatim.test.ts` (behaviour, default on, speaker filter, budget, index at the link, tick, the Fired counter, the reserve row); `test/rp-verbatim-bench.test.ts` (synthetic chain: the planted details found, the share of ordinary scans that bring a passage); `test/rp-verbatim-parts.test.ts` (#539: a chat in parts, the part a reply reads, past the old 3.5 MB, an edited part, a v2 index, a build that ran out of time, door B's order by passage vectors).
- **Why / history:** #264, #184 step 8; the bench of 2026-11-07 showed a fixed "three shared words" rule brought a passage for 78% of ordinary scans, which is why the rule is statistical.
- **Trap:** the index is rebuilt by the tick only when the chat's Litopys record has a new `rev`; an edit of a finished chat's messages that does not touch its record shows after the next rebuild of that chat. The reserve row exists only for a chat that has a link; a new reader of the links file must keep both in step. The trace shows the passages of the newest reply only.

### Prompt board switch keys
- **Touches:** `meta.promptBoard.off` in the chat file; `PROMPT_BOARD_OFF_KEYS` and `PROMPT_BOARD_OFF_RE` and `cleanPromptBoard` (engine plugin); readers in `plugins/litopys`, `plugins/relations`, `plugins/world`; `src/lib/carries.ts` (`CarrySwitch`, `switchKey`); `src/components/canvas/prompt-board.tsx`; `src/lib/prompt-order.ts` (order keys for "said", "journal", "persona memory").
- **Must stay true:** every key the board writes is in `PROMPT_BOARD_OFF_KEYS`, or matches `PROMPT_BOARD_OFF_RE` (`section:` or `book:` with a name). `cleanPromptBoard` drops any other key when the chat is saved. The same key turns the same part off in the assembly, in the carries strip and in the reserve.
- **Enforced in:** `plugins/engine/plugin.js` `PROMPT_BOARD_OFF_KEYS` `PROMPT_BOARD_OFF_RE` `cleanPromptBoard`; `src/lib/carries.ts` `CarrySwitch`; `plugins/litopys/plugin.js` `offForChat`.

### Two kinds of dice (on purpose, owner 2026-11-11)
- **The model's die: `roll_dice`** (`plugins/tools/plugin.js`, the Dice Roller tool, off until turned on). The model decides when to roll and what to roll (`count`d`sides`, a modifier, an optional `dc`, up to 20 dice of up to 1000 sides). The tool uses `Math.random`, no seed, so asking again gives another number. The result goes back to the model as the tool's answer, inside that reply's tool loop; the app keeps the exchange with the reply (`tools` of the message, `toolX` in the engine plugin). Nothing else reads it. Rewinding is the message's own: a swipe or a regenerated reply makes a new call and a new roll, and a deleted message takes its roll with it.
- **The World DM's check** (`plugins/world/plugin.js`, "the dice", World DM settings: Dice mode, stat, chance). Code rolls before the reply is written, with no model call: first a chance gate (percent), then 2d6 plus a modifier from one of the character's Dashboard numbers (a twentieth of it, -5..+5; `auto` takes the cast's numbers), read through `DICE_BANDS` (up to 5 miss, 6-7 no but, 8-9 yes but, 10 and more full success, shifted by the tilt). The line rides the reply request like the DM's event (`insert` hook), is shown in the prompt Inspector as "Dice", and the model is told to follow it (strict mode: no softening). The pace die and the life die use the same seed and bands. The roll is **seeded** (`seededRandom`, seed = chat id, the key of the chat's last message, the message count, the operation and the swipe number): a reload or an identical request gives the same roll, a swipe changes the seed and rolls again. Each roll is logged to `world/dice/<chat>.json` (newest 60, with where in the chat it belongs, so the app can mark it under its reply); `undoFrom` and `settle` rewind the DM's records, fronts and event, not this log, so a swiped-away reply keeps its old row until it scrolls out of the 60.
- **Must stay true:** the two never feed each other. `roll_dice` is not seeded and is read only by the model; the World DM's check is seeded, rolled by code and decides what the reply is told. Do not unify them without the owner: a model-called tool and a code-called check differ on purpose (who may roll, and whether a swipe re-rolls identically).
- **Enforced in:** `plugins/tools/plugin.js` `rollDice` (called from `handleTool`); `plugins/world/plugin.js` `seededRandom`, `rollFate`, `rollFateAuto`, `DICE_BANDS`, `diceInsert`, `logDice`.
- **Fails in:** `test/rp-tools.test.ts` (roll_dice), `test/rp-world.test.ts` (seeded rolls, bands, the log).
- **Trap:** a reader who sees "dice" in both plugins and merges them loses either the model's free choice of any die or the repeatability of the DM's check across a reload.
